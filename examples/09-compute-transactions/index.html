Compute-heavy transactions with an early write

This is a candidate workload for testing whether early conflict detection can avoid expensive speculative work. It is not a constructed proof that the custom runtime outperforms GNU TM.

Algorithm and hypothesis

Every transaction flips one bit of a shared uint32_t, acquiring a write reservation early in the custom STM. It then computes a configurable sequence of shifts, XORs and unsigned additions in a private value, and finally publishes the result. Every iteration contributes to the final result. An independent serial recurrence verifies it outside the timed region. All transactions apply the same transformation, so the final result does not depend on their order.

A runtime that rejects a conflicting writer before the compute phase may avoid work that a different protocol would later discard. Whether GNU TM actually incurs that cost depends on its selected algorithm and contention management, which this example does not force or identify. Shared ownership may also serialize the custom runtime and outweigh any saving.

Four implementations

  • sequential.c: ordinary serial reference.
  • internal.c: explicit private API registration, read, early write, private compute, final write and external retry controller.
  • directive.c: omp transaction; the direct compute helper is automatically prepared.
  • gnu_tm.c: GNU TM with a transaction_safe compute helper.

Build, validate and run

make -C examples/09-compute-transactions check
examples/09-compute-transactions/.build/directive 4 128 4096
make -C examples/09-compute-transactions experiment

Arguments: threads, total transactions, compute steps per transaction. Defaults: 4, 128, 4096. Limits: 1–8 threads, 1–10,000 transactions, 1–1,000,000 compute steps and at most 100,000,000 total steps. Unsigned 32-bit wraparound is defined. Timing includes team startup, transaction execution and the final barrier; serial validation and output are excluded. Actual team size is checked.

Exploratory comparison

experiment.py runs 30 randomized rounds with 2, 4, 6 and 8 threads and 16, 1,024 and 16,384 compute steps per transaction, using 128 transactions. There are 1,080 measured executions and 36 discarded warmups. It needs the benchmark dependencies and writes raw data, summaries, paired-bootstrap mean ratios and PNG/SVG graphs into a new .build/experiment-TIMESTAMP directory. Pointwise 95% bootstrap intervals use 5,000 resamples; no outliers are removed.

Directive, internal and GNU TM may optimize helpers differently. The internal callback uses a stable control argument; the directive registers the preexisting steps parameter. The internal version links statically while directive links dynamically. Thus differences measure complete implementations, not only conflict policy. Inspect generated code and profile before attributing a timing difference to avoided retries. No conflict counts are collected.

Initial exploratory result

The initial 30-round experiment found no custom/GNU TM ratio with a pointwise 95% interval entirely below one. Directive mean ratios ranged from 1.015 to 1.393; internal ratios ranged from 0.870 to 1.360. A lower observed mean alone is not sufficient evidence of a performance advantage. This candidate narrows some gaps but does not establish that GNU TM is slower.
