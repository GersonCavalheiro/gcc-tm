Índice

Os comandos partem da raiz do repositório. As instruções abaixo preservam o guia operacional do projeto; os relatórios históricos descrevem a cobertura de cada etapa, não uma execução nova.

Preparar o ambiente

Em Ubuntu 24.04, instale as dependências de compilação e dos testes:

sudo apt-get update
sudo apt-get install -y build-essential binutils bison flex libgmp-dev \
  libmpfr-dev libmpc-dev libisl-dev zlib1g-dev libzstd-dev python3 perl \
  texinfo gawk dejagnu expect tcl git ca-certificates xz-utils

Alternativamente, a partir da raiz do repositório, prepare o contêiner:

docker build -f Dockerfile.gcc-tm -t gcc-tm-dev .
docker run --rm -it -v "$PWD:/usr/src/gcc-tm" -w /usr/src/gcc-tm gcc-tm-dev

Execute a configuração e compilação abaixo dentro desse shell. Para os testes DejaGNU, instale também dejagnu expect tcl na imagem (a receita atual não os inclui); isso pode ser feito acrescentando-os à lista de pacotes do Dockerfile antes de construir a imagem. O volume preserva fontes e resultados no host. Use o mesmo ambiente para construir e executar: binários gerados no contêiner podem exigir uma glibc mais nova que a disponível no host.

Compilar fora dos fontes

Todos os comandos seguintes partem da raiz do repositório, salvo indicação. Configure um diretório de build novo, sem reutilizar configurações ou binários de outra máquina/ambiente:

mkdir -p gcc-build
cd gcc-build
../gcc-src-tm/configure \
  --prefix=/usr/local/gcc-tm \
  --enable-languages=c,c++ \
  --enable-libgomp \
  --disable-multilib \
  --disable-bootstrap \
  --disable-libsanitizer \
  --disable-libquadmath \
  --disable-libssp \
  --disable-libvtv
make -j"$(nproc)"
cd ..

Essa configuração corresponde à usada no build local de desenvolvimento e evita dependências de bibliotecas de 32 bits. --disable-bootstrap reduz o trabalho de compilação, mas não realiza a validação de um bootstrap completo. Ajuste o número de tarefas à memória disponível. Se gcc-build já contiver um build incompatível, use outro diretório vazio e adapte os comandos, inclusive GCC_BUILD nos exemplos.

Não é necessário instalar o compilador para desenvolver ou testar. Após mudanças, make -C gcc-build -j"$(nproc)" atualiza o build. Para alterações restritas às respectivas camadas, os relatórios também usam:

make -C gcc-build/gcc -j"$(nproc)" all
make -C gcc-build/"$(gcc-build/gcc/xgcc -dumpmachine)"/libgomp -j"$(nproc)" all

Confirmar que está usando o GCC em desenvolvimento

Use caminhos explícitos: gcc --version sozinho pode mostrar o GCC do sistema, e o número 16.2.0 não comprova a presença da extensão. Na raiz do projeto:

export GCC_TM_ROOT="$PWD"
export GCC_TM_BUILD="$GCC_TM_ROOT/gcc-build"
export GCC_TM_CC="$GCC_TM_BUILD/gcc/xgcc"
export GCC_TM_TARGET="$("$GCC_TM_CC" -dumpmachine)"
export GCC_TM_GOMP="$GCC_TM_BUILD/$GCC_TM_TARGET/libgomp"

"$GCC_TM_CC" -B"$GCC_TM_BUILD/gcc/" -v
"$GCC_TM_CC" -B"$GCC_TM_BUILD/gcc/" -print-prog-name=cc1
"$GCC_TM_CC" -B"$GCC_TM_BUILD/gcc/" -B"$GCC_TM_GOMP/" \
  -L"$GCC_TM_GOMP/.libs" -print-file-name=libgomp.so
command -v gcc

O cc1 deve apontar para gcc-build/gcc/ e a libgomp para o build selecionado. xgcc é o driver ainda não instalado; -B seleciona seus componentes. Alterar apenas o PATH para incluir gcc-build/gcc não faz gcc virar xgcc.

Compile um exemplo real e confira também a biblioteca carregada em execução:

"$GCC_TM_CC" -B"$GCC_TM_BUILD/gcc/" -B"$GCC_TM_GOMP/" \
  -I"$GCC_TM_GOMP" -fopenmp -ftransaction-debug \
  transaction_test/transaction_aninhamento.c \
  -L"$GCC_TM_GOMP/.libs" -Wl,-rpath,"$GCC_TM_GOMP/.libs" \
  -o /tmp/gcc-tm-aninhamento
LD_LIBRARY_PATH="$GCC_TM_GOMP/.libs${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}" \
  ldd /tmp/gcc-tm-aninhamento
LD_LIBRARY_PATH="$GCC_TM_GOMP/.libs${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}" \
  /tmp/gcc-tm-aninhamento
nm -D --defined-only "$GCC_TM_GOMP/.libs/libgomp.so" | rg 'GOMP_transaction_'

Na saída de ldd, libgomp.so.1 deve resolver para o diretório do build. A biblioteca deve exportar GOMP_transaction_begin, GOMP_transaction_register e GOMP_transaction_end (versão GOMP_NEWTM_1.0). -ftransaction-debug habilita os diagnósticos específicos do compilador; os logs do runtime são independentes. Erros de símbolo/versão GOMP_NEWTM_1.0 geralmente indicam uma libgomp antiga ou do sistema. As primitivas internas newtm_* não devem ser exportadas na DSO. O comando rg acima pode ser substituído por grep se ripgrep não estiver instalado.

Executar os testes

Exemplos e rastreamento

Depois de concluir o build:

make -C transaction_test -B check

O Makefile usa ../gcc-build/gcc/xgcc, inclui -fopenmp, seleciona a libgomp local e grava executáveis/logs em transaction_test/.build/. O verificador exercita máximo paralelo com 1, 2 e 4 threads solicitadas, empate, aninhamento e registro/liberação dos objetos. O alvo check também depende de check-internos, que executa corpos STM preparados manualmente e ligados ao archive local; portanto não se limita ao rastreamento. Para outro build:

make -C transaction_test -B check GCC_BUILD=/caminho/absoluto/do/build

O Makefile atual fixa o alvo x86_64-pc-linux-gnu; em outra plataforma, adapte GOMP_BUILD ao alvo informado por xgcc -dumpmachine. Use -B no make para recompilar ao trocar compilador ou flags. make -C transaction_test run apenas executa os exemplos; check verifica seus resultados.

O alvo check-lifecycle testa criação e limpeza reais do contexto, transferência da lease, aninhamento, falhas, leitores compartilhados e descarte sem publicação. Liga ao archive estático da libgomp selecionada e usa os cabeçalhos privados em gcc-src-tm/libgomp/. Esse alvo cobre o ciclo de vida; registro/acesso STM e commit têm testes específicos no modo funcional:

make -C transaction_test -B check-lifecycle
# Para outro build:
make -C transaction_test -B check-lifecycle GCC_BUILD=/caminho/absoluto/do/build

Execute Python sem -O/-OO e sem PYTHONOPTIMIZE: o verificador depende de asserções e recusa sua desativação. Esse teste verifica retornos, preservação de dados, logs e visibilidade dos símbolos, sem executar transações reais.

Modo funcional, provas e LTO

Os alvos especializados selecionam verificadores distintos; check sozinho não executa toda a matriz de certificação. Exemplos de seleção:

make -C transaction_test check-internos
make -C transaction_test check-abi-v1
make -C transaction_test check-leituras check-escritas check-chamadas
make -C transaction_test check-integracao
make -C transaction_test check-grafo-atual
make -C transaction_test check-grafo-lto
make -C transaction_test check-contraprovas-lto

check-internos testa serviços privados em corpos preparados manualmente. check-abi-v1 testa a ponte exportada; leituras/escritas/chamadas e integração exercitam a geração STM pertinente. Os alvos de grafo e contraprovas verificam a atualidade da evidência e as recusas integradas. Cada verificador delimita sua própria matriz: esses comandos não significam cobertura de toda combinação possível. As matrizes maiores podem ter custo elevado; selecione-as conforme a camada alterada.

Carga parametrizada de leituras e escritas

make -C transaction_test check-carga
make -C transaction_test check-carga CARGA_THREADS=8 CARGA_REPETICOES=10000
transaction_test/.build/transaction_carga 4 1:9 1000

O executável recebe três parâmetros: número de threads, relação escritas:leituras e repetições por thread. O Makefile executa 1:9, 1:1 e 9:1, por padrão com 4 threads e 1.000 transações por thread, também incluídas em make check. O teste verifica contagens, valor final e consistência do objeto; o verificador confere ainda registros/liberações da hash. Logs em transaction_test/.build/transaction_carga-*.log.

Uma repetição corresponde a uma transação de leitura ou de escrita (read-modify-write). Para N repetições e pesos W:R, cada thread executa floor(N*W/(W+R)) escritas. Os pesos e sua soma devem caber em uint32_t, e a soma deve ser positiva. Threads/repetições devem ser positivas, e o total de transações deve caber em unsigned long long. Falha se o ambiente limitar a equipe abaixo do número solicitado. Nesse exemplo em modo de rastreamento, um critical externo à diretiva protege os valores, incluindo registro e liberação. Isso exercita a infraestrutura atual, sem comprovar isolamento transacional.

Criação e destruição da tabela hash

make -C transaction_test -B check-hash-create-destroy

O teste usa os fontes reais e headers privados do build Linux x86_64, ligado ao archive local, para verificar argumentos inválidos, overflow, capacidades 1/3/1024, mutexes utilizáveis e preservação integral em BUSY. Uma entrada retida é preparada internamente para isolar esse teste do caminho de aquisição. Saída em transaction_test/.build/hash_create_destroy.log; aceita GCC_BUILD como os outros alvos. Não comprova quiescência, concorrência ou STM funcional. Os printf/fflush de depuração foram mantidos fora dos mutexes dos buckets.

Aquisição e consulta de entradas

make -C transaction_test -B check-hash-acquire

O teste interno verifica inserção/reutilização, consulta sem inserção, tamanho incompatível, nulos, overflow por injeção controlada, colisões e concorrência com quatro threads. Verifica também liberação parcial/final e destruição de metadados fora do lock. A mistura nativa é exercitada com endereços numéricos consecutivos e alinhados, capacidades arbitrárias e bits superiores; isso não é execução nativa da variante de outra largura. Saída em .build/hash_acquire.log dentro de transaction_test; aceita GCC_BUILD. A ponte usa referências reais e verifica os retornos, preservando os printf fora dos mutexes. Não há STM funcional.

Consultas e visita de metadados

make -C transaction_test -B check-hash-entry

Endereço e tamanho são imutáveis e consultados sem lock enquanto o chamador mantém uma referência. A visita executa o callback uma vez sob o mutex do bucket, preservando a referência. O teste verifica os campos, instalação/substituição de metadados, argumento nulo, destruição final, visitas concorrentes com quatro threads e progresso em outro bucket. Usa o build privado Linux x86_64 e admite GCC_BUILD. Callbacks não fazem E/S, espera ou reentrada; printf/fflush da primitiva ficam fora do lock. Log em transaction_test/.build/hash_entry.log, com limite de 60 segundos. Não comprova STM funcional.

Contagem consistente de entradas

make -C transaction_test -B check-hash-count

Count adquire todos os mutexes em ordem crescente, conta entradas (não referências), satura em SIZE_MAX e libera em ordem inversa. O teste cobre tabela vazia, referências repetidas, colisões, capacidades 1/3/1024, saturação por injeção interna restaurada e contagem concorrente com quatro threads. Verifica também zero durante destruição de metadados ainda em andamento, sem chamar destroy nesse intervalo: zero não autoriza destruição nem comprova quiescência. Usa configuração privada Linux x86_64, aceita GCC_BUILD e grava transaction_test/.build/hash_count.log, com limite de 60 segundos. Printf/fflush ficam fora dos locks; não chamar count de callbacks de visita ou destrutores, nem com mutex de bucket já adquirido.

Diagnósticos sem inversão de locks

make -C transaction_test -B check-hash-diagnostics

O teste interno Linux x86_64 mantém stdout ou stderr bloqueado enquanto outra thread inicializa a ponte ou recebe falha de alocação injetada. Verifica que nenhum log/diagnóstico fatal retém o lock global ou o mutex do bucket, mantendo os formatos printf existentes. Quatro casos isolados: inicialização, OOM de entrada, tabela e buckets. OOM continua fatal (saída 1); cada caso tem limite de 10 segundos. Logs em transaction_test/.build/hash_diagnostics-*.log (relativos à raiz); aceita GCC_BUILD. Interposição restrita ao teste, sem hooks ou ABI novos. Em concorrência, o log create pode sair depois de operações que já observaram a tabela publicada. A finalização agora usa o controle de admissão e participações descrito abaixo; tabelas independentes continuam exigindo quiescência externa.

Admissão e encerramento da tabela global

make -C transaction_test -B check-hash-owner

O proprietário usa OPEN -> CLOSING -> CLOSED. O contexto externo retém uma participação até concluir toda a limpeza; aninhamentos reutilizam-na. Durante CLOSING novos usuários são recusados, mas os existentes podem terminar. newtm_hash_owner_close, interface interna oculta, é não bloqueante quanto à drenagem: retorna BUSY com usuários/coordenador/entradas residuais e pode ser repetida após conclusão/join. Um único coordenador destrói a tabela drenada; CLOSED não reinicializa e chamadas repetidas não destroem duas vezes. Consumidores internos diretos da tabela global devem manter uma lease por todo o intervalo de uso e referências; não podem destruir a tabela emprestada.

O finalizador automático faz uma tentativa: se ocupado, conserva a tabela e o controle para recuperação pelo processo, sem esperar ou forçar limpeza. O mutex de admissão sobrevive à tabela para rejeitar chamadas tardias. Isso não garante segurança de dlclose: impedir execução atual/futura da biblioteca continua sendo responsabilidade externa. Não há nova ABI pública GOMP ou semântica STM.

O teste Linux x86_64 cobre onze casos em processos separados, com limite de 15 segundos: sem uso, aninhamento, coordenadores concorrentes, limpeza e log de criação pendentes, entradas residuais, corrida de admissão, erros/overflow, chamada tardia e finalização com usuário ativo. Logs em transaction_test/.build/hash_owner-*.log (relativos à raiz); aceita GCC_BUILD.

Suítes DejaGNU do compilador e da libgomp

A rodada de aceitação de 2026-11-10 registrou 629 PASS nas seleções transaction/critical de C/C++ e libgomp. Veja o relatório e runner reproduzível, incluindo seleção de libgomp.spec para o driver não instalado.

Com DejaGNU/Expect/Tcl instalados e as variáveis GCC_TM_* acima definidas:

export LD_LIBRARY_PATH="$GCC_TM_GOMP/.libs${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
export OMP_NUM_THREADS=4
export OMP_DYNAMIC=FALSE

make -C "$GCC_TM_BUILD/gcc" check-gcc \
  TESTSUITEDIR=testsuite-tm-c RUNTESTFLAGS='gomp.exp=transaction-*'
make -C "$GCC_TM_BUILD/gcc" check-g++ \
  TESTSUITEDIR=testsuite-tm-cxx RUNTESTFLAGS='gomp.exp=transaction-*'
make -C "$GCC_TM_GOMP" check \
  RUNTESTFLAGS='c.exp=transaction-*.c c++.exp=transaction-*.c'

É essencial selecionar a libgomp local também na execução: passar apenas GCC_UNDER_TEST/GXX_UNDER_TEST como variáveis make não bastou na auditoria. Confira os comandos efetivos em .log e os resultados em:

  • gcc-build/gcc/testsuite-tm-c/gcc/gcc.sum e gcc.log;
  • gcc-build/gcc/testsuite-tm-cxx/g++/g++.sum e g++.log;
  • gcc-build/<alvo>/libgomp/testsuite/libgomp.sum e libgomp.log.

Para verificar regressões em critical, repita os três comandos separadamente, substituindo transaction-* por critical-* e usando novos TESTSUITEDIR, por exemplo testsuite-critical-c e testsuite-critical-cxx. Preserve os .sum e .log da libgomp antes de repetir, pois a chamada seguinte os sobrescreve. Não repita o mesmo driver .exp com filtros diferentes numa única chamada: um filtro pode substituir o outro.

Procure FAIL, XPASS, UNRESOLVED e erros de infraestrutura; confira também se houve testes executados. A auditoria registra resultados históricos de subconjuntos, não aprovação da suíte completa nem evidência de STM funcional. Para ampliar a cobertura, make -C gcc-build -k check executa as suítes dos componentes configurados e pode demorar bastante.

Checkpoint da base atual

Após reconstruir a libgomp, execute no ambiente do build:

make -C transaction_test check-checkpoint-contexto CFLAGS='-O2 -Wall -Werror'

O checkpoint contexto_pronto_para_registro reúne hash, owner, criação/limpeza de contexto e rastreamento. Logs e relatório JSON ficam em transaction_test/.build/checkpoint_contexto_pronto_para_registro/. O cabeçalho do teste delimita sua cobertura; aprovação não certifica isolamento ou STM funcional.

A etapa 2 de geração de código materializa descritores internos de identidade com objeto lógico, extensão, deslocamento, kind e verificação de limites sem wrap. make -C transaction_test check-descritores valida os campos gerados. A ponte padrão continua de rastreamento; ABI executável, clones e instrumentação STM estão implementados no modo funcional opcional, dentro do domínio aceito no parecer final.

Validação dos exemplos desta documentação

Os programas completos dos capítulos de exemplos e de serviços podem ser copiados para arquivos .c fora de docs/. Use as variáveis GCC_TM_* definidas acima:

"$GCC_TM_CC" -B"$GCC_TM_BUILD/gcc/" -B"$GCC_TM_GOMP/" \
  -O2 -fopenmp -fopenmp-transaction-stm exemplo.c \
  -L"$GCC_TM_GOMP/.libs" -Wl,-rpath,"$GCC_TM_GOMP/.libs" -o exemplo
./exemplo

Para o exemplo manual da ABI, substitua as opções OpenMP por -I"$GCC_TM_ROOT/gcc-src-tm/include" e acrescente -lgomp -pthread depois do fonte. O controlador já está escrito explicitamente nesse programa.

A aceitação de 2026-11-11 é delimitada no parecer final: 93 negativos/45 controles na matriz de diagnóstico e 629 PASS em seis seleções DejaGNU, além das regressões transitivas descritas no parecer. Isso não equivale a um bootstrap completo ou a uma nova execução dessas matrizes a cada edição documental. Artefatos de teste ficam em transaction_test/.build/ e não substituem os fontes e contratos versionados.

Conferência desta edição documental

Em 2026-11-11, os quatro programas C completos apresentados nesta documentação (depósito, transferência, mini carga e controlador manual da ABI) foram extraídos dos blocos de código, compilados com o build local em -O0 e -O2 e executados: oito execuções aprovadas. Os destinos dos links locais do README e das páginas também foram conferidos. Logs e relatório da conferência ficam em transaction_test/.build/docs-validation/; são artefatos locais, não requisito para leitura da documentação. Essa conferência não repetiu as suítes completas de aceitação.

Exemplos em quatro versões

Consulte examples/. Para compilar: make -C examples. Para comparar com a referência sequencial: make -C examples check. Cada subdiretório também possui Makefile e alvo check. GNU TM requer a libitm construída na árvore local.
